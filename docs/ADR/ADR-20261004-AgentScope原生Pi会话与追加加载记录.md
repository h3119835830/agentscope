# 原生 Pi 会话与追加加载记录

日期：2026-10-04。状态：采纳。

## 决策

1. 第二层共用当前任务，使用三个页签，任务准备与 Pi 对话同页、策略审核与启动加载同页、完整加载记录独立页。第三层仅移除顶部介绍。
2. 沿用锁定 Pi SDK，通过 SessionManager 的原生消息与压缩接口恢复上下文；AgentScope 保存公开条目而不是 SDK 原始磁盘会话，隔离 HOME 为临时目录。这样既保持原生消息角色与 SDK 会话处理，也不把模型私有思考或凭据写入长期状态。
3. 工具证据每轮重新读取。持久化的旧公开回复不替代当前来源；轮次快照冻结来源列表和候选引用。上一版候选以 Draft 和独立版本元数据提供，正式提案与校验输入的对象合同保持明确。
4. 解释回合允许无候选，后台只认校验和提交工具产生的记录；一次成功提交产生一个新候选。校验与提交采用相同的已读取证据和历史检索前提，避免“校验通过”后才发现无法提交。
5. 继续复用构建、编译、批准、ActPlaneProvider 与 broker 绑定回查。加载请求增加可选标识，启动前先追加尝试，关联部署 ID 在事务中写入。新增记录不覆盖既有候选、批准、部署。
6. 中断或服务重启保留公开状态、撤销凭据；只恢复任务的启动前状态，不自动重新加载。解释已批准版本时，单纯失败、中断或重启不清除旧批准。

## 取舍

公开会话恢复不保留私有推理；旧轮次的工具事实在新轮重新读取，因此会消耗每轮预算，但来源归属、证据漂移与可回查输入明确。SDK 原始 JSONL 会包含不适合长期落盘的内容，本实现不直接保存它。

普通 GitHub 资产快照有大小和格式限制，未登记的大文件、二进制与外部资源不能自动形成执行规则。保持现有 write/unlink 能力；语义约束作为 guidance，必要而不支持的执行要求阻断批准。

旧手工批准合同保持兼容，新增 Pi 会话不追溯作废旧版本。新 Pi 候选提交后工作台重新进入构建审核流程；每个版本仍绑定其实际候选与上下文。

审计列表采用数据库过滤分页，详情展开才加载快照。旧记录缺字段时诚实展示“未记录”，不从任务现状补造历史批准、回执或时间。

## 记录展示补充决策

重复名称的历史任务及加载尝试采用一个主条目加默认关闭的历史折叠区。分组使用仓库、完整 commit、任务名称；不同固定场景或不同完整 commit 分别展示。保留当前历史任务选择；旧实例展示 ID、时间、状态和可展开原任务，避免把不同目标误当成同一个可修改任务。只调整展示，不删除或合并数据；每次加载回执仍独立。分页先由既有接口执行，前端仅组织当前页，保留精确任务筛选和实际记录总数。
