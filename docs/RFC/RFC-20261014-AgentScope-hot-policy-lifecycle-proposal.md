# AgentScope 不重启 Agent 的策略增量管理方案

2026-10-14 后续收敛决定：增量的当前目标为真实 ActPlane 域，固定基线只有系统/Agent；本提案仍未实施，本轮收敛不批准其完整热更新引擎改造。 见 [当前合同](RFC-20261014-AgentScope-agent-baseline-runtime-policy.md)。历史验收及既有批准范围不变，本轮仅文档修订。

2026-10-14 粒度补充：本提案继续保持待批准、未实施。稳定域/epoch 仅解决已有执行域的更新连续性，不提供共享进程内的 session_id 区分。应用前须按 [执行绑定重推 RFC](RFC-20261014-AgentScope-execution-binding-rederivation.md) 核验真实执行与可用性影响闭包；不支持局部目标时拒绝，不以热更新扩大为整个域。

本轮只读研究 ActPlane/AgentScope 源码、当前二进制身份和官方资料，仅保存本方案及去敏研究索引。不改源码、服务配置、内核程序或当前策略，不提交候选，不批准/应用策略，不启停 Agent/Broker，不建立定时任务，不 Git push。

## 1. 目标与建议

推荐采用“**稳定执行域 + 版本化生效策略快照 + 可信管理员提交**”。Agent 的主 PID、进程开始身份、generation、domain、原生会话和已建立合法上下文保持；策略更新另用 policy_epoch 计数。用户可以按文档逐步增加、修改、停用、恢复和删除，内部编译完整下一版本，然后切换生效快照。每次应用仍由用户确认，批准只保存决定。

第一版允许应用切换时短暂停顿目标进程树，随后原进程继续执行；不承诺完全无停顿，不用停止/启动执行器冒充热更新。暂停时长必须实测并显示，超出窗口就中止或保持明确暂停，不悄悄重启。新工具门禁不能代替对子进程和后台执行的约束。

本方案第一版处理现有平台支持的 ActPlane DSL 文档及其结构化配置，不同时改普通业务授权、挂载权限、seccomp 或其他进程启动合同。此类变更不支持热更新时明确拒绝该模式，不自动落回重启应用。

## 3. 交互和权限合同

| 用户操作 | 控制面动作 | 内核动作 |
| --- | --- | --- |
| 新增/修改 | 保存版本、生成差异候选，保留其余已生效文档 | 应用确认后激活包含新增/修改文档的新快照 |
| 停用 | 候选把目标文档标为 inactive，其他层与文档保留 | 新快照同时排除该文档的 enforcement rules 及来源/变换/gate updates |
| 恢复 | 新候选重新引用明确版本，并重新评估停用期间的状态缺口 | 通过状态/能力检查后激活；不假定缺失期间的历史完整 |
| 删除 | 未生效配置可归档；已生效配置先生成停用/删除候选 | 应用后退出活动集合；旧快照、审批和审计仍保留，之后才回收无引用运行槽 |

界面始终为“生成候选 → 批准变更 → 单独确认应用”。确认页列出中文策略名、增删差异、运行/停止实例数、预计暂停方式、实际覆盖和不支持原因。审批含现行 base_epoch、目标进程身份、策略快照哈希、编译器/内核能力、状态迁移说明；任何漂移要求重新校验。保存、勾选和批准均不切换内核策略。

系统内置不可移除底线可在可信实现中单独保存，不构成第五个用户配置 scope。系统策略由系统策略管理员操作，Agent 本层只能改自己的文档；停用本层不能解除系统/平台约束。必须为可信管理入口增加“替换自己拥有的策略版本”权限检查，Agent 提议者继续只能提议。不能给 Agent 通用删规则、清标签、写 BPF map 或改父域的权力；approved_by 文本本身不构成授权。

## 4. 引擎建议实现

### 4.1 发布单位是不可变快照

为当前执行域增加独立的 `policy_epoch` 与活动快照引用。新快照包含各层文档版本、编译 rules/updates、稳定标签/gate 映射、能力与所有者元数据；平台底线保持独立不可停用。控制器先 stage 新快照，当前执行仍使用旧快照；通过授权检查后 commit 切换活动引用。

建议接口：`stage_policy_snapshot`、`commit_policy_snapshot(expected_epoch, approval_ref, request_key)`、`policy_status`、`retire_policy_snapshot`。这是新增接口设计，不是已经存在的 ActPlane 命令。普通 append 路径继续保留其子域收紧边界。

内核一次事件读取并携带同一个快照标识，source/update/rule 判断不得各自重新读取活动版本。跨 tracepoint 与 LSM 的一个操作也要明确记录所属 epoch；不能只换 rules 而让 updates 仍用旧版。系统批次的不同实例各有 watch/执行域，单个域的提交不能称为全系统原子提交。

实现首选“不可变策略存储 + 单一活动描述符”；存储可采用 map-in-map 或带版本键的规则 bank，先通过 Linux 6.6 verifier/性能原型选择。Linux [map-in-map 文档](https://docs.kernel.org/bpf/map_of_maps.html) 支持快照存储的组成方式，但不提供整组多 map 的事务保证，不能把一次 map update 直接当作完整应用证明。

旧快照须等内核读者不再引用且审计元数据持久化后回收；回收协议未验证前不重用槽位。不重用仍被进程/文件标签引用的 label 位，不把旧标签位重新解释成新含义。容量不够时提前拒绝，当前保护继续，不先清表再重新装载。

### 4.2 状态保留与迁移

- 未变化的来源定义、标签、gates、invalidators 保持身份，已有进程/文件污染事实保留，不用 clear_runtime_state 来更新策略。
- 系统和 Agent 文档中的标准 AGENT 映射稳定、可核验的当前原生主体与后代身份。仅“为每个新文档定义一个新的 exec 标签”可能漏掉已运行主体；迁移只能依据真实绑定/已记录来源，不能伪造 exec 或给不满足来源条件的所有进程加标签。
- 新 source 从激活后的事件开始收集；新规则依赖此前未知的读文件/网络来源历史时，预览必须标明生效起点。要求覆盖未知过去的严格策略拒绝本次无重启应用，不能把标签缺失当作未读过秘密。
- 原测试成功 gate 只有在命令定义、exit 条件和新鲜度要求相同且证据完整时延续；定义改变必须失效。执行过测试不等于测试通过。
- 停用不清洗已存在的秘密标签或抹去审计。恢复遇到采集间隙需要重新判定，不能自动当成干净上下文。

### 4.3 完整应用事务

1. 用户批准后的显式应用请求，带候选/批准哈希及冻结目标；Broker 持久化已授权应用意图和幂等键。
2. 在旁路准备新快照，检查继承、容量、hook/profile、句柄及状态迁移。不改生效引用。行为验证在专用隔离验证域进行，不读取真实凭据、不对正式资源运行攻击探针。
3. 先核验审批冻结的逻辑目标、共享主体、执行单元和暂停/终止影响，冲突或漂移拒绝；再关闭真实影响范围的新工具门禁，等待既有任务达到安全边界；超时默认中止，继续旧策略，不杀任务冒充成功。后台执行仍在旧策略下，直到正式切换。
4. 第一版短暂冻结目标 cgroup 及后代，确认 `cgroup.events:frozen=1`、成员身份与不可迁移约束；同时设置受保护的内核更新屏障。仅工具门禁不足，freezer 也不能被当成所有异步 I/O 已完成的证明。[Linux freezer 合同](https://docs.kernel.org/admin-guide/cgroup-v2.html#core-interface-files)。
5. 对每个实际执行域提交新 epoch，内核检查可信调用者、文档所有者、不可移除底线和 expected_epoch。批次保持暂停，直到所有目标成功；未运行实例只更新下一次启动配置，不自动启动。
6. 读回内核 epoch/快照哈希/作用域及当前绑定，持久化真实应用回执，再更新控制面投影；恢复原进程，不重发已执行工具请求。暂停长度记录 P50/P95/最大值；首版暂定切换冻结窗口上限 5 秒，须经隔离性能与 8 秒保护期限回归后确定，不能直接宣称已达到。
7. 若提交后状态不明或只有部分目标提交，全部目标保持明确暂停并报告已知 epoch；没有新的人工确认，不自动恢复较宽的旧权限、不自动重启。提交前失败且旧状态核验完整时，可以中止新快照并继续旧策略。

内核读回是生产每次提交的加载证明；隔离 allow/block 实验是行为证据，两者分别展示。不能为了显示成功而在正式 Agent 上自动跑破坏性探针。

### 4.4 Broker、审计和保活必须同步

现保护指纹把任意 pin/watch 文件变化看作故障。热更新需要一个有期限、可核验的策略事务：保活仍持续核对 Agent/watch/cgroup/平台底线，新 epoch 只能来自已批准意图，不能通过暂时关闭保护检查来躲过 watchdog。新策略对象在旁路 stage，不先混进受监控 pins；提交后绑定明确的策略对象清单与快照哈希。

`generation` 表示进程代次，`policy_epoch` 表示同一代次内的策略版本。加载回执改为至少按 `(instance_id, generation, policy_epoch)` 保存，不能覆盖本代次旧回执。内核事件、工具开始/结果、反馈及监控记录都带 epoch、规则来源与版本；删除后的事件仍能正确还原当时的中文策略名和规则正文。不同版本不因 rule_id 槽位复用而混淆。

API 短暂离线时，Broker 继续维持已批准且可核验的活动 epoch；新审批等待恢复。恢复后只按已持久化批准意图与当前内核事实协调投影，旧数据库快照/旧 PID 不恢复权限。重复请求只读回同一真实结果，不再次执行工具或切换。

## 5. 无重启覆盖范围

| 场景 | 首版目标与限制 |
| --- | --- |
| 已运行 Node/Python 与后台后代，新增文件访问限制 | 对当前主体与已存在后代立即覆盖未来受支持的事件，不能等再次 exec 才生效；必须以真实读取/写入和内核事件验收 |
| 已打开 FD 的后续 read/write/truncate | 使用现有 file_permission 等路径，分别验证写入结果、文件内容及事件，含 dup/继承/跨路径变体；未通过则该类变更不可热应用 |
| 已建立可写 mmap 的后续内存写 | 当前钩子不能可靠撤销已有可写 PTE。首版明确拒绝需要收回此类访问的严格变更；不静默杀子进程或重启 Agent。未来需单独设计映射撤销机制或经用户另行同意回收工具执行域 |
| 网络限制 | 当前支持的是新 connect 等已实现钩子；要求停止已有连接 send 的变更，须新增 socket_sendmsg 等覆盖并验收后才支持，不能只改白名单 |
| 新增秘密来源/跨事件规则 | 保留已知事实；未知过去不能重建。用户明确知晓从哪个时间点生效；严格全历史要求不支持时拒绝，而非伪造完整保护 |
| 单个 Agent 与系统策略 | 单 Agent 只影响本实例；系统批次对全部冻结目标统一协调；子域不能借停用本层解除父域约束 |
| 原生共享会话 | 第一版仍以实际受控执行域为范围，不能用共享 PID 声称实现单会话独立策略 |

“不重启”表示支持范围内的更新不更换 Agent 进程身份，不等于任意新安全语义都可追溯收回已经发生的效果。能力判断与不支持原因必须在用户应用前出现。

## 6. 既有三个运行 Agent 的迁移

**现有 Broker 没有无损交接接口，退出会停止实例，旧恢复逻辑也会回收已登记域。因此不能直接 restart Broker 部署新功能，也不能承诺当前三个实例立即支持新引擎。**

先在独立环境的新实例开发和验收。既有三个实例继续由当前 Broker/引擎保护，期间不迁移、不改策略、不替换 watch。正式迁移前单独给出并验证计划：保持旧执行保活/原生网关和对象状态，核验旧 pins/map ABI/links/主体身份；证明可信监督权交接及加载对象切换不触发旧 watchdog，也不触发清状态/旧域回收。

如果旧实例的当前合同无法安全交接，就保留它们在旧环境；新能力先用于新建实例或用户日后主动安排的迁移。不能用隐藏的重启、修改现有进程内存、绕过保护指纹或直接清 BPF 状态实现“无损升级”。现有实例迁移是否能做到零重启是独立验收项，未验证不能标为通过。正式迁移、具体目标和正式策略应用继续由用户分别确认。

## 7. 不采用的快捷做法

- 直接清 cap_policy 位图：缺失来源/变换/gate 的停用语义、所有者授权、版本和审计；并不能解决状态与容量回收。
- 重新 watch/attach 同一 PID：新旧引擎并行可能让旧规则继续生效，退出旧引擎又可能清状态/触发 Broker 故障；不是已证明无损切换。
- 换子域但保留 PID：域内标签、文件来源和 gate 状态不能天然转移，且旧后代/FD 绑定可能遗留，不作为默认路线。
- 用可清除的临时标签模拟停用：将策略生命周期混入信息流标签，可能误解除父域约束或污染其他规则，不作为通用实现。

## 8. 实施顺序与验收门槛

1. **能力原型**：固定源码/二进制/内核 profile，在独立 DB/socket/BPF pin/cgroup 的 DSH 和 Hermes/必要 Python 测试主体上，复现现有 append、标签与规则容量行为。验证新主体标签问题、FD、mmap、已连接 send 边界，保留失败结果。
2. **版本化引擎**：stage/commit/retire、所有者权限、原子可见性、稳定状态映射、容量/回收及事件 epoch；做 verifier/竞争/崩溃与中断原型，通过后定稿 ABI。阶段一的 append 演示不能代替完整增删验收。
3. **AgentScope 接入**：独立热应用路由及审批基线、Broker 保护核验、加载回执/队列、中文预览/停用删除状态。不改旧 apply 的事实描述，也不默认回退到重启路径。
4. **持续真实验收**：相同 PID/开始身份/generation/domain/session，在新增→停用→恢复→删除循环后执行中文真实任务；核对内核拒绝、对应反馈、允许对照及合法任务完成。DSH 先跑，再做 mini-swe-agent 独立对照；不能拿固定探针替代模型完成任务的证据。
5. **迁移验证与单独确认**：隔离证明旧 Broker/引擎交接，失败则保持现有正式实例；交付代码 diff、RFC/ADR/REVIEW/BUG、实验记录及回滚/恢复合同。用户确认后才安排正式迁移；每次策略应用仍单独确认。

最低验收用例：

- 相同 PID、start_ticks、generation、domain 和原生 session，更新期间无重复工具执行；合法任务继续完成。
- 保存/候选/批准三阶段内核 epoch 不变；显式应用才切换。
- 新增限制后真实违规动作拒绝，有同 PID/domain/epoch/rule 的内核事件及安全反馈；合法对照成功。
- 停用指定文档后该文档效果消失，其他文档及父域保护继续；删除保留历史；恢复重新评估状态缺口。
- shell、Python、后台已存在子进程、fork/exec 竞争与跨 Agent 隔离；错误所有者/旧批准/错 epoch/重复请求拒绝或幂等。
- 更新期间高并发 syscall 不观察半份规则；提交前失败保留旧保护，部分提交/回执丢失如实暂停、恢复不自动扩权。
- FD/mmap/现有连接按覆盖矩阵验收；不支持案例的应用请求提前拒绝，且没有偷偷重启。
- 超过现 128 rules/320 updates/64 labels 等累计边界的增删循环，不能因累积历史耗尽而清表；GC 不改变旧事件解释，不复用在途快照/活标签。
- API 中断、保护指纹漂移、队列满、监督权交接失败和 8 秒安全机制仍按合同工作；能力测试仅在隔离环境注入故障。
- 同步检查并维护 RFC、ADR、REVIEW、BUG；本提案获批后才把采纳决策写入 ADR，不把研究推演标为内核验收通过。
