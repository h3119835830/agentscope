# RFC：以已发布模板约束策略生成 Agent

日期：2026-10-14。状态：用户已批准实施；接口、模板子配置与助手已完成隔离验证并发布到 18003，发布结果见 REVIEW。未改动 ActPlane 内核 ABI，策略应用继续由用户确认。

## 1. 目标与约束

策略助手根据用户给出的场景和要求，选择系统已发布的模板、填写允许配置的参数、建议应用层级，形成与手工配置一致的候选记录。助手不得新增模板语义、随意输出 DSL、改写系统继承约束、批准候选或调用执行面。实际应用继续由用户确认。

助手的只读策略资料限定为系统策略的授权投影与已发布模板。场景描述、用户要求和被允许使用的资源引用作为本次请求输入，由可信服务提供结构化事实；不因此授予助手终端、任意文件读取或凭据读取能力。现有 Agent 策略的合并、去重和继承冲突由后端处理，不要求模型读取完整配置或敏感内容。

模板不足时应输出“缺少哪个能力/参数”，保留用户原意。不得以扩大到整个 Agent、降低为提醒或生成界面不存在的策略来完成请求。

## 3. 统一模板合同

建立由服务端维护的已发布模板注册表；系统页与 Agent 页可以保持不同的用途和展示入口，但应引用同一份版本化合同。模板记录包含：

- 稳定 ID、版本、中文名称、来源及维护者。
- 固定的保护语义、操作组、效果和允许的例外；必须阻止的规则不能由助手改成 notify。
- 参数 Schema：类型、必填、枚举、路径匹配模式、字节/数量上限和是否允许通配符。未知字段拒绝。
- 可应用层级和身份要求；只列当前执行层支持的范围。
- 所需编译器、钩子、运行特性和能力证据；不满足时只能说明或起草。
- 确定性的 AST/结构化生成器、反馈文案及可读表单映射。
- 合法操作、拒绝操作、间接执行变体的验证依据与已知限制。

名称、说明、已有样例和编译成功标记不能代替模板合同。模板修改产生新版本，旧候选不能在模板升级后静默改变含义。用户自建模板亦须经过受信任维护流程和独立验证；策略助手没有创建或发布模板的权限。

## 4. 助手权限与输出合同

助手可检索已发布模板、读取系统约束投影、提出必要的参数澄清、返回模板实例化计划。工具权限必须由后端身份/路由白名单约束，不能仅依赖系统提示词。

输出计划只包含以下类别，字段名为设计建议，尚非现有接口：

- 已发布模板引用：`template_id`、`template_version`。
- 参数：严格符合该模板 Schema 的 `parameters`。
- 建议目标：用户所选 Agent 的引用与所需 scope；实际目标身份由服务器绑定。
- 参数出处：用户要求或可信资源引用，缺少时列入待澄清。
- 需补充的模板/执行能力：明确的 gaps，不能混入可应用配置。

禁止返回自由 DSL、任意命令、任意 source/label 表达式、审批决定、加载参数或伪造运行核验。路径参数须转为可信登记资源下的规范对象，防止借路径字符串注入规则。执行来源从受控启动身份取得，不由模型填写 `exec "**"`。模板需要确定命令身份时，不以任意 python/node 进程充当可信检查器或生成器。

在实现入口时，不把管理员配置库的通用保存接口直接暴露给助手；助手只能提交候选。手工管理员仍可使用既有受权编辑能力，其改动记录来源并走现有审批。

## 5. 同一套配置、审批和界面

建议流程为：用户选择目标与场景 → 检索模板 → 助手填参/澄清 → 服务端实例化并校验 → 候选展示在对应配置界面 → 用户编辑核对并提交 → 现有审批和显式应用 → 执行面核验与反馈。

服务端实例化前检查模板版本、参数、身份、路径、继承与能力；再使用可信生成器构造 AST/规则，复用既有编译与提案合同。记录冻结的模板版本、配置参数、系统/目标基准、目标身份和产物哈希；审批及应用前再次核对。新配置按明确变更集合合并已有配置，保留不相关策略，拒绝陈旧覆盖及重复请求。

配置记录同时支持手工与助手来源。对应界面直接显示中文策略名称、保护对象、操作、处置、作用范围和状态；详情使用同一参数表单。助手对话保留解释和候选链接，不另建一份只能在聊天里查看的策略库。来源是助手不代表应用范围是会话。

状态分别呈现待补充、草案、待审批、已批准待应用、已应用，以及当前执行保护核验。保存候选不自动勾选、不自动批准、不启停 Agent。当前审批/应用可能重载执行器；本提案不承诺不重启，热更新另按生命周期方案评审。

系统策略默认只读继承。单场景的资料保护不自动上升为全局系统策略；只有用户明确提出全局规则且其权限允许时，才生成相应系统候选。工作区/会话范围不支持时保留该目标和阻塞原因，不自动改成 Agent 级。下层候选不能解除上层禁止，权限开放仍由现有权威访问配置决定。

## 8. 为什么现有内容不能覆盖所有 OS 策略

覆盖必须同时满足三层：真实钩子/执行机制可观测并可约束，编译器/加载器能表达并装载，该参数化模板具有正确合同。只增加模板数量不能弥补底层机制缺失；也不能因论文给出语法就认为当前部署已全部支持。

ActPlane 的主要表达面是文件访问/变更、程序执行、网络事件、来源标签传播、执行链与事件顺序门控，具有 block/notify/kill 等效果。论文的保证限定在配置钩子收到的事件，并排除若干语义、内容及旁路问题：[ActPlane v2 §3](https://arxiv.org/html/2606.25189v2)。因此目标应是“覆盖已验证能力集合和常见场景”，而非“覆盖所有可能的 OS 策略”。

当前应单独说明：写入/删除别名的粒度、执行参数的前置拦截限制、IPv4 connect 与已有连接发送的差别、已有可写映射与新增 mmap/mprotect 的差别、IPC 等未验收通道、工作区/单会话绑定，以及正确转账/备份完整等业务语义。资源配额、任意系统调用过滤等也需要相应 cgroup/seccomp 或其他经集成的执行能力，不能让模板凭空声称支持。

应维护能力矩阵：事件、匹配器、条件、效果、层级、运行证据、合法对照、拒绝变体。计划覆盖率的分母必须是冻结版本的能力/场景集合；两个模板列表的条目数不能作为安全覆盖率。

## 9. 实施顺序和验收条件

1. 盘点两套预设，去重并对齐真实访问组、效果和运行限制。先形成共同服务端模板合同及能力矩阵。
2. 统一手工参数表单与模板实例化接口；不改变现有审批授权边界。
3. 助手只输出模板选择及参数计划，所有生成候选通过同一受限入口；历史自由 IR/DSL 记录保留只读，不能冒充新模板候选。
4. 先覆盖订单日报、代码修复/测试保护、插件凭据访问、审计完整性等具体场景，再扩展信息流与流程门控。缺少执行能力的模板不发布为可应用。
5. 仅在隔离实例验收：未知模板/版本、额外字段、DSL 注入、越界路径、下层解禁、伪造目标、陈旧审批和重复请求均拒绝；手工与助手同参同产物；合法工作完成且拒绝证据/反馈可关联；生成不改变当前运行策略。

## 11. 已实施的接口填参与模板子配置

统一服务端注册表目前包含 15 个 Agent/工作区模板和 12 个系统预设合同，共 27 条。新增文件读取、文件修改与删除、变更范围例外、程序执行、网络连接、任意指定文件来源到新连接的信息流等模板；保留原有六类模板的稳定内部 ID。此数量是目录条目数，存在组合与重合，不代表覆盖全部 OS 策略。

静态模板是父记录；每次手工或助手填参新增一条同级子配置。新增“禁止修改”不覆盖已有“禁止删除”，也不修改父模板的默认值。父子关系用于组织配置，不是策略域继承或事件先后门控。每个子配置独立版本化，保存模板版本/合同摘要、参数、目标层级、资源映射摘要、原始操作意图及实际执行访问组。

接口为 `GET /api/policy-templates`、`POST /api/policy-template-configurations`、`POST /api/policy-template-configurations/{id}/versions`、`/{id}/proposals`、`/{id}/archive`，以及 `POST /api/agent-instances/{id}/template-configurations/generate`。后者调用现有配置模型产生模板参数调用计划，再执行与手工保存相同的服务端参数校验和实例化合同。没有浏览器自动化、终端工具、自由 DSL 输出、审批或加载工具。生成只保存草案；真实模板、参数、路径、目标和效果由服务端限制。

生成请求可在 Agent 停止时保存 Agent 基线的参数草案。缺少可信工作区身份时不生成伪造工作区目标；工作区独立应用仍阻塞。系统模板在系统入口明确配置，Agent 场景助手只读系统约束，不把局部要求自动写成系统规则。旧系统配置有明确模板引用时，在相应父模板下只读投影，并返回原系统配置入口操作；不迁移或覆盖原版本。旧助手草案仍保留只读与原审批入口。

系统模块的“策略与模板”展示父模板和子配置；Agent 助手展示其准确目标下的子配置与生成记录。二者使用同一参数表单和提交合同，审批复用原有状态机。提交前核对范围；批准后仍单独确认应用。停用只生成移除当前文档的候选，保留其他子配置；删除仅归档未应用配置并保留版本。重新校验采用当前子配置版本，重新绑定来源；模板、子配置、资源映射或符号链接发生变化时，旧候选不能直接加载。

写入和删除当前共用访问组。子配置保留分别填写的意图，但不能伪称分别强制执行。单一操作配置在提交前明确展示实际影响两者，并要求人工确认该差异；确认保存在冻结提案绑定中。新生成规则的执行反馈也说明共享访问组的实际影响，避免误导执行 Agent。本次没有通过“先删除再修改”模拟不存在的内核区分能力，也没有修改 eBPF、编译器 ABI 或现有 Agent 权限。

新审批、生成和读取接口仍受现有本机/管理员控制面认证保护；原生受控 Agent 凭据不能访问。模型只接收系统约束、发布模板、登记资源事实和用户本次材料，不接收凭据或文件正文；路径核验由可信服务执行。生成批量全量校验后原子保存，失败不留下部分子配置，幂等重试不重复新增。模型请求不持有执行面更新锁。
