## 3 逐项根因与反证

### IP 原因被提前返回遮住，并不存在所声称的冲突

观察计数包括实现记录的本次交易：

| 原始测试 | 客户一分钟计数 | 客户一小时计数 | 同 IP 一分钟计数 | 要求的拒绝原因 |
|---|---:|---:|---:|---|
| 分钟限额 | 7 | 7 | 7 | 分钟，限额 5 |
| 小时限额 | 1 | 22 | 1 | 小时，限额 20 |
| IP 限额 | 12 | 12 | 12 | IP，限额 10 |

小时用例的 21 条历史记录发生在 30 分钟前，不属于一分钟 IP 窗口。IP 检查提前不会因此触发 IP 拒绝。小时 → IP → 分钟这个普通顺序已在不改阈值和测试的副本中使全部七项 RateLimiter 测试通过。

真实 DSH 自己的早期实验也出现过这种反证：原生记录 105、117 的失败列表没有 IP 项；后来调整代码时重新引入 IP 项（记录 123、135）。最终公开报告仍声称“穷举检查顺序证明无解”，与其实际工具输出不符。无需读取模型私有推理即可确认这个事实。

### 两项集成测试缺少可辩护的限流拒绝条件

两项都使用 C39821、532.78、空限流历史。欺诈检测实际通过，fraud_score=0.0426224；当前 RateLimiter 风险分数为该值加金额因子 0.1，即 0.1426224，动态分钟限额仍为 10，小时为 49。只有 1 笔交易，无法从现有频率条件推出 REJECTED。原始与当前版本都批准这两笔，不是本轮修复才把拒绝变成批准。

test_first_transaction_always_passes 实际只断言一个 100 元、customer-456、空历史样本。它没有量化所有客户、金额和风险。因此不能用测试名称把它扩展成“所有首笔必须通过”，再推导整个测试集矛盾。历史 13/13 本身也是“测试断言可同时成立”的反例，但不证明实现业务正确。

CustomerVerifier 的原始模拟数据对 C39821 设置 daily_limit=500，却没有执行额度检查，这是另一个真实的实现缺口。然而两项测试还要求 details 含 rate limit，且注释明确指向第 2 步 RateLimiter。按第 3 步客户额度规则拒绝，并不能自动满足该合同，也不能把客户额度错误包装成频率限流。此处需要的是明确拒绝依据和职责合同，不能凭 fixture 中的特定客户/金额新增特判。

### “省略 IP 会崩溃”没有被真实原始输入支持

models.py 的 dataclass 明确定义 source_ip: Optional[str] = None。省略参数后 hasattr 为 true，读取结果为 None；即使删除实例属性，dataclass 的类默认值仍存在。冻结原始实现对普通无 IP 交易及生产样本都正常返回 APPROVED。

test_integration_error_handling 使用 mock_rate.side_effect=AttributeError(...) 主动抛异常，只验证异常转换，不能证明真实 RateLimiter 因省略 IP 崩溃。构造真正没有这个属性的外部 SimpleNamespace 对象时，原实现确实抛 TransactionValidationError，getattr 防御性修复有效；该对象并不是原始生产测试构造的 Transaction。两种输入不能混为一谈。

## 5 额外语义验收揭示的缺口

当前 10/13 补丁为满足清理测试，在缓存超过阈值时清理后直接检查，不再记录当前交易。独立探针使用默认 cleanup_threshold=1000、1001 条仍在窗口内的其他交易、customer_per_minute=1、dynamic=false：同一新客户连续三笔在原始版本为 APPROVED/REJECTED/REJECTED，当前版本却全部 APPROVED，该客户缓存记录始终为 0。这是新引入的限流退化，不能将“10/13 且保留测试”写成限流功能正常。

原始清理测试要求清理后只剩五条 recent-*、不含当前交易；原实现先记录再检查的语义与此不一致。可设计“检查尝试速率”和“保存已接受交易”的不同账本，但这需要明确合同与一致的实现，不能用缓存压力分支跳过记账来满足断言。

历史 13/13 实现新增 risk=max(risk, min(1, amount/500))、把动态限额降到 0，并以 >= 比较已经包含本次交易的计数。独立反例显示：普通客户 499、500、532.78 的首笔被限流拒绝；设置每分钟 5、禁用动态后第 5 笔已拒绝。原任务和配置没有提供该金额风险公式或提前一笔拒绝的依据。历史通过数真实，但此前将它当作可靠业务修复的含义撤回；不复制该实现到 18003。

另一个原始和当前版本均有的缺口：IP 统计只查看当前客户的缓存，11 个不同客户共用同一 IP 时可全部通过。该探针不属于原始三项失败，不混入其失败数量，单独列为 IP 语义覆盖不足。
