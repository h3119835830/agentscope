# 控制台重启引发 Agent 停止及总览读取超时

状态：执行保活与总览热点已整改、隔离验收通过并正式部署；最终版本 24 小时观察截止 2026-10-13 22:57:30（北京时间），尚未通过。数字地址的 IAB 挂起独立开放。

## 已确认原因

今天一次 API 发布退出超出旧 Broker 8 秒健康期限，三个受控实例因此被停止，随后恢复为新 generation。发布评审原件在技术文档 REVIEW-20261012-AgentScope-policy-targets-step1.md。旧代码把管理面健康当作执行面存活依据，形成发布故障的扩大链。systemd 日志另显示 API 停止超时；不能把所有用户看到的停止都归为同一个原因。

本次运行环境从 10 月 10 日启动，未找到对应时段的 WSL 重启和 OOM 证据；10 月 7 日未托管服务随 WSL 停止属于历史事件，不能套用到今天。今天正式 API 检查返回 200，而 IAB 数字地址页面仍超时，说明页面失联与进程退出需分开记录。

采样到 API 高 CPU 时，py-spy 显示多个 worker 在 `console.summary → history.catalog.page(limit=1) → eligibility.blockers → agent_context.revalidate`，继续扫描 artifact 和调用原生上下文核验。即使只要一条目录结果，也做了完整历史资格计算；取消浏览器等待没有终止这些同步工作。原始线程栈、进程时间线及 systemd 摘要存于同日 evidence 目录。此证据定位了总览热点，不能推导其他慢接口已全部消除。

首轮正式发布后仍采到 API CPU 432.33%、总览中位耗时 2572.825 ms，没有据此关闭性能问题。再次采样发现 managed worker 每 0.2 秒重读 128 条任务，其中 80 条已结束任务占约 11.8 MB；反馈扫描及待审批计数也反复加载完整历史状态。修复按阶段选取活动任务、终态日志变化后补采、待审批候选预筛选后，10 次请求短样本总览中位 341.28 ms、最大 527.92 ms，API 5 秒采样 CPU 77.39%。这只说明当前短样本改善，未证明饱和负载或长期尾延迟已解决。保留两轮性能结果与线程栈。

## 修复与验证

Broker 每秒改为执行保护核验，并由独立 runner 保留 8 秒失效终止。gateway 准入和回执在本地 root 持久队列处理。控制台只投影已提交事实；断控不扩大权限。总览改 SQL 聚合，健康异步返回，后台任务并发退出及请求排空有界。

隔离实验两轮包含 45 秒 API 离线、合法原生工具执行、越权写入拒绝及哈希不变，恢复同一 PID/generation，队列回补和旧调用拒绝；最终 watch 丢失 1.003 秒终止，Broker 卡住后独立 runner 7.923 秒终止（时钟和轮询有误差，实际原生退出由 8 秒期限驱动）。首轮用保留文件名作为 canary 导致启动探针冲突，已改成普通合成文件并保留问题说明。核心载荷首轮缺读取钩子预留，九条载入失败被保留，启动配置修正后整套重测。

首次 Broker 升级按明确捕获的三个活动目标受控换代，策略及 DSL 文档/修订保持一致，原先关闭的实例未启动。随后 API 单独重启及性能补丁发布，三个运行实例 PID/generation/domain/策略均保持。后端完整测试 1152 通过、11 跳过；前端 258 通过，构建通过。跳过项不能计为通过。
