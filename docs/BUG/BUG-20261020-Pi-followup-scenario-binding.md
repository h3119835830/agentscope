# BUG：Pi 澄清后选取旧场景文件并生成错误路径候选

日期：2026-10-20。状态：真实正文读取及续问来源延续已通过；可应用候选仍受路径能力限制。禁止审批此前错误候选。

## 复现事实

精确 RQ5 DSH 实例 `instance-1f4469579e8947f4` 中：

1. 读取器修复后，新请求明确指定 rq5-policy-read-20261020 场景。
   “本次参考”显示 `/w/0/rq5-policy-read-20261020/task.md`，目录与正文操作成功。
2. Pi 询问 README/tests 路径与其他保护范围。操作者确认其列出的场景路径，
   要求保留现有约束、继续实际读取，不指定模板、不批准或加载。
3. 下一轮“本次参考”却显示 `/w/0/task.md`，未读取指定场景 README。
   生成 6 项草案，目标为 `/w/0/transaction-verification-service/...`。
4. 实际场景项目路径为
   `/w/0/rq5-policy-read-20261020/workspace/transaction-verification-service/...`。

旧根目录仍属于同一 Agent 的登记资源，并非读取器越权或身份绕过；
但它不是本轮任务的正确资料，不能将其候选作为本场景验收成果。

## 风险与处置

人审若仅查看“生成成功”就批准，会保护错误位置，造成虚假安全证明。
已保留 6 项草案和读取记录，未提交、批准或应用，未删除证据。

## 代码核验与整改

本轮确认 `conversationFor` 只回传需求/问题/缺口/候选数量；生成入口每轮新建读取 Agent，
没有传递已读正文、读取回执或冻结候选参数。新增服务端父请求延续，复核真实来源后恢复上下文；
目录浏览结果加入实际执行路径；未新增场景专用提示词，ActPlane 保持原样。
同根双 task.md、累计来源、重复读取、跨 Agent/阶段、资料/代次/资源漂移均加入确定性回归。
模型是否正确完成实际 RQ5 多轮读取，仍必须以新界面证据验收，不由单测替代。

进一步核对真实 DeepSeek 客户端：旧读取循环每轮重新构造 system+user 两条消息，
未保留模型上一轮 assistant 工具请求。真实失败的安全诊断为第二轮返回 dict、
仅一个未识别的协议字段，已完成一次目录浏览但未读正文；未保存原始返回，不能断言具体字段。
改为保留 assistant 请求与实际工具结果的分角色消息序列，所有调用仍经过原有工具/路径/身份校验。
新增客户端级测试核验消息长度 2→4→6、角色次序、真实目录/正文结果及私有推理不回放。

角色修复后界面仍失败：本次安全诊断包含 configurations/questions/gaps/summary 的合法类型，
另有一个未知字段；不能将此失败归因于读取权限。原调用链把协议错误直接抛给操作者，
没有将校验失败反馈给读取 Agent。现增加最多两次固定协议反馈，拒绝整个非法响应、
不宽松剥离字段；实际调用、来源复核与审批门槛不变。真实复验结果在本轮 REVIEW 记录。
