## 图对应的产品模型

平台 D0 定义稳定的底线；任务 D-A / D-B 继承底线并增加场景约束；测试子域 D-A1 再缩小权限。shell、pytest 等普通后代进程延续所属域，不能因为页面多画了一个 PID 就认为创建了独立安全域。

```text
平台基线：秘密文件 + 私钥 + 平台策略保护
    ├─ 编码任务：工作区写范围 + 提交/测试要求
    │    └─ 测试子域：进一步限定 tests 目录
    └─ 研究任务：数据范围 + 网络目的地 + 输出隐私要求
```

统一展示以下四项，但分别标明执行方：

1. 平台继承约束：在子域中锁定，用户和 Agent 不能取消。
2. 场景约束：Agent 读任务、仓库和环境，实例化目录、命令与资源。
3. 运行时新增约束：展示新增原因、目标域、影响范围、批准及加载回执。
4. 通用语义约束：如隐私、证据、不得越权承诺，显示由内容检查、Agent 或权威业务接口执行，不算作 OS 强制保护。

`policy(D) = policy(parent(D)) + local(D)` 是继承关系。当前平台是否真正形成跨任务 D0，仍需检查可信加载与绑定实现；基线版本字段不能代替真实父域证据。子域不能通过改名字、覆盖 reason、增加例外 gate 或降为 notify 来绕过父规则。平台调整底线应创建新版本；既有会话需要单独确认合法迁移路径与加载回执。

## 三种处置需要准确说明

| 选择 | 用户看到的含义 | 必须满足的能力 |
|---|---|---|
| block + 反馈 | 在相关操作执行前拒绝，返回限制原因和允许的下一步；Agent 可以继续工作 | 相应 BPF-LSM pre-op hook、目标匹配、绑定和实测；反馈另需送达证据 |
| notify | 操作继续，只记录事件并给出提醒 | 能观察该事件并送达反馈；不能标成“已阻止” |
| kill | 终止命中事件的违规进程，反馈原因 | 当前 tracepoint 实现为事后处置，不承诺副作用从未发生，也不自动终止整个 session |

kill 与 block 不是一个简单的“安全强度”滑块。即使引擎冲突仲裁按 `kill > block > notify`，也不能推论 kill 比事前阻断更能保证数据未改变。若产品要“先阻止副作用，再终止整个会话”，应建模为两个动作并分别验收：事前拒绝 + 可信控制面的域/进程树终止，不能假装一个 kill effect 已经完成两件事。

本次只运行了 4 个 `actplane compile --json --rule` 离线检查，没有 load/attach/run：

| 检查 | 编译 ok | 支持报告 | 含义 |
|---|---|---|---|
| `block read file "/workspace/.env"` | true | supported / pre_op=true / bpf-lsm | 静态能力支持；没有证明真实会话保护生效 |
| `block exec "git" "commit"` | true | **unsupported / pre_op=false** | 警告 `argv_block_exec_post_exec_only`；必须阻止 UI 误报 |
| `block exec "git"` | true | supported / pre_op=true / bpf-lsm | 能禁用该可执行程序整体，不会区分 git 子命令 |
| `kill exec "git" "commit"` | true | supported / pre_op=false / tracepoint | 事后终止；不是事前拒绝 |

原始报告见 `evidence/compile-support.json`；环境/二进制标识另见 `evidence/compile-environment.json`。此结果属于该编译器/静态主机能力，不是当前 session 的内核加载验收。

## Git 分支规则如何落地

需求本身合理：用户选择仓库、操作、分支模式、处置和反馈，例如 `main → kill`、其他分支 `block + 原因`。但普通 `git commit -m ...` 不带当前分支参数；[Git 文档](https://git-scm.com/docs/git-commit)说明提交更新当前分支/HEAD。因此不能写 `exec "git" "main"` 就认为完成了 main 保护。

实现前需要明确区分：创建 commit 对象、更新本地 main 引用、向远端 main 推送。它们是不同的安全目标。推荐将“禁止直接改变受保护引用”作为可验收目标：可信侧识别仓库、实际 git-dir/worktree、HEAD 与目标 ref，绑定到获准操作，强制中介引用更新和发布。需要覆盖 lock/rename、packed-refs 或 reftable、`update-ref`/`commit-tree`、`--git-dir`/`-C`、detached HEAD、并发切换分支和其他 Git 客户端；单次读取 HEAD 后放行存在竞态。

远端主分支保护还应使用托管平台的权威权限/分支规则，并检查远端回执。仅限制某条 git argv，不能保证其他客户端或协议不产生同等副作用。当前原型允许填写 main/其他分支处置，但醒目标明“不可执行的需求草案”，不输出看似可用的分支 DSL。

## 对 RQ1 原始翻译的修订要求

- `ruflo::30`：禁止 secrets/.env 提交，被翻译为 SECRET 标签上的 `block git commit`，当前后端不支持参数级事前 block；标签来源也不等于扫描暂存区。不能直接采用。
- `cc-connect::29`：原文要求 `go test ./...` 成功，YAML 仅是任意 `go` 后 notify，缺 `test`、`exits 0`，因此不能作为“测试已通过”的证据。
- `pi::36`：`reset`、`.`、`-A` 等单 token 过宽；如不区分子命令，可能误伤正常命令。语法编译不等于语义等价。
- `planning-with-files::5`：原文有 master 与 tag 例外，YAML 禁全部 `--force/--force-with-lease`，没有完整表达例外。
- `llmfit::17`：任意 python 祖先不等于获准的生成器。真实性需要可信命令/产物验证。
- `ironclaw::28`：对 auth/cors 文件 notify 不会证明没有削弱鉴权。需要内容评审与测试，界面应标为语义/内容检查。

这些是原始研究条目到生产模板之间的语义与能力差异，不是新增提示词即可修复的问题。原始 YAML 保留在目录证据中，模板以新的 ID 和修订说明引用。

## 推荐界面结构

**会话 → 安全**是主入口，首屏回答“目前保护什么、谁规定的、会怎样处置、真的生效了吗”。统一记录表显示规则与对象、操作、处置、来源、状态；支持对象搜索和继承/本会话来源筛选。反馈原因在记录详情中查看，DSL、研究证据和能力边界继续折叠。来源页单独展示平台、任务与子域的继承关系。

**平台 → 安全底线**选择模板、路径、操作、处置和原因。处置选项随能力变化：参数级 Git 的事前 block 应禁用并解释；main 分支规则只能存为需求。默认反馈可以恢复，自定义反馈应有长度限制并通过结构化序列化进入 AST/DSL，不能直接拼接。保存原型不会提交任何真实安全变更。

**待处理变更**显示 Agent 为何新增、约束哪个域、父域规则、范围前后变化与预期反馈。合法收紧仍要核实权限与可用 hooks；扩权需更高权限、新批准以及合法重建路径，不能让 Agent 覆盖继承规则。

**安全检查**分开显示草案、编译与能力支持、批准、加载、PID/domain 绑定与活性、独立阻断探针、反馈送达。历史命中不证明当前在线；未验证要直接显示未验证。实际案例建议用：误读 `.env`、shell/Python 间接删除保护数据、测试子 Agent 越界修改、main 引用更新四类，分别验证直接/脚本/隐藏路径与正常近边界操作。

## 下一步实施与验收

先把 session 权限清单和文件保护模板接入真实能力报告与加载回执；再接 Agent 场景提案与收紧增量；最后完成 Git 引用/发布中介后开放分支级配置。建议每个模板具备：来源、语义目标、参数 schema、后端能力、默认 reason、正常路径、违规路径、绕过路径、范围和生命周期证据。

文件验收应覆盖 read/write/unlink、truncate、rename/替换、符号与硬链接、已有 FD/mmap、后代进程、启动前/后绑定；按目标明确支持或拒绝。网络验收覆盖 IPv4/IPv6、DNS、代理、UDP、已有连接和秘密来源传播。Git 验收覆盖可信分支识别、原子 ref 更新与其他客户端。每个案例既检查内核事件/处置，也检查受保护对象完整性和 Agent 反馈。

本轮完成的是研究来源核对、静态编译能力检查和原型交互验收；没有新加运行时安全能力，也没有运行真实秘密访问、Git 发布或破坏性探针。具体验收结果见 REVIEW 文档。
